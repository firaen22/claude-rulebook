# Agent Skills: Production Engineering Workflow

You are operating under a disciplined, 6-phase development lifecycle. AI coding agents default to the shortest path — skipping specs, tests, and security reviews. This skill enforces production-quality process over prototype shortcuts.

**Core rule**: Never skip a phase gate. Each phase requires explicit completion before proceeding.

---

## Phase 1: DEFINE — Spec Before Code

**Trigger**: Any task > 30 minutes, multi-file changes, unclear requirements, or architectural decisions.

**Skip only for**: Typo fixes, unambiguous single-line changes.

### Process

1. **Surface assumptions first** — List every working assumption before writing spec. Unspoken assumptions are the most dangerous form of misunderstanding.

2. **Write SPEC.md covering**:
   - **Objective**: One sentence — what problem does this solve and for whom?
   - **Functional requirements**: What it must do (numbered, testable)
   - **Non-requirements**: Explicitly state what's out of scope
   - **Tech stack & constraints**: Frameworks, external APIs, performance targets
   - **Directory structure**: Where new files will live
   - **Code conventions**: Naming, patterns, error handling approach
   - **Testing approach**: What constitutes "proven correct"
   - **Success criteria**: How we know we're done

3. **Get human sign-off** before proceeding. The spec is a contract, not a suggestion.

### Anti-Rationalization Table
| Excuse | Reality |
|--------|---------|
| "Requirements are obvious" | Write them anyway — obvious things get misunderstood |
| "I'll spec it after I prototype" | Prototypes become production; specs don't get written |
| "It's too small to spec" | Small tasks that go wrong waste more time than speccing them |

---

## Phase 2: PLAN — Task Breakdown

**Process**:

1. **Plan-mode only** — Read codebase, don't write code yet. Understand existing patterns before proposing new ones.

2. **Dependency mapping** — Visualize component relationships. What must exist before what?

3. **Vertical slicing** — Build complete feature paths, not horizontal layers.
   - ✅ `auth → profile → settings` (full user flow)
   - ❌ `all DB models → all API endpoints → all UI` (layers first)

4. **Task structure** — Each task must have:
   - Description (one line)
   - Acceptance criteria (testable)
   - Verification steps (how to prove it works)
   - Dependencies (what must complete first)
   - Size estimate: **S** (1-2 files), **M** (3-5 files), **L** (6-8 files, split further if > 8)

5. **Checkpoints every 2-3 tasks** — All tests pass, core flow works. Never accumulate broken state.

**Red flags**: Any task touching > 8 files needs splitting. Circular dependencies mean the architecture is wrong.

---

## Phase 3: BUILD — Incremental Implementation

**Core pattern**: Implement → Test → Verify → Commit → Next slice

### Rules
- One thin vertical slice at a time. Each increment leaves the system in a **working, testable state**.
- Never write > 100 lines without running tests.
- Touch only the code required for the current task. No opportunistic refactoring.
- Keep the codebase compilable throughout. Use feature flags for incomplete work.
- Commit each working slice: `git commit` = save point.

### Slicing Strategies
- **Vertical slice**: End-to-end for one user action (e.g., full CRUD for one entity)
- **Contract-first**: Define API interface → build frontend and backend in parallel
- **Risk-first**: Tackle uncertain/hard parts first to validate assumptions before dependent work

### Red Flags
- Writing > 100 lines without a test run
- Mixing unrelated changes in one commit
- Scope creep ("while I'm here I'll also...")
- Building abstractions before you have 3+ concrete examples
- Refactoring alongside feature work (obscures which change caused a regression)

---

## Phase 4: VERIFY — Prove Correctness

**Tests are proof, not optional extras.**

### Process
1. **Unit tests**: Pure functions, edge cases, error paths
2. **Integration tests**: Component interactions, API contracts
3. **End-to-end tests**: Full user flows through the system
4. **Manual verification**: Golden path + 3 edge cases

### Exit Criteria (must ALL pass before Review)
- [ ] All new code has tests
- [ ] Tests cover happy path AND error paths
- [ ] No regressions in existing test suite
- [ ] Build passes with zero warnings
- [ ] Type-check passes (`tsc --noEmit` or equivalent)
- [ ] Linting passes
- [ ] Manual smoke test on golden path

### Anti-Rationalization Table
| Excuse | Reality |
|--------|---------|
| "I'll add tests later" | Later never comes; untested code ships |
| "It's too simple to test" | Simple things break in surprising combinations |
| "Tests slow me down" | Tests prevent the 2-hour debugging session next week |

---

## Phase 5: REVIEW — Quality Gates

### Five-Axis Evaluation Framework

**1. Correctness**
- Does it meet the spec requirements?
- Are error paths handled?
- Are edge cases covered by tests?

**2. Readability**
- Names follow project conventions?
- Control flow is clear (no nested ternaries, no 5-level callbacks)?
- No unnecessary complexity?

**3. Architecture**
- Consistent with existing patterns?
- Clean module boundaries (dependencies flow in one direction)?
- Appropriate abstraction level (not over- or under-abstracted)?

**4. Security**
- Input validation at system boundaries?
- No secrets in code or logs?
- Auth/authz enforced at every entry point?
- Parameterized queries (no string interpolation in SQL)?
- External data treated as untrusted?

**5. Performance**
- No N+1 query patterns?
- No unbounded operations (pagination enforced)?
- No unnecessary synchronous blocking?
- Hot paths free of heavy allocations?

### Review Sizing
- ~100 lines changed: optimal
- ~300 lines: acceptable for cohesive changes
- 1000+ lines: **split before reviewing**

### Feedback Labels
- **Critical**: Must fix before merge (correctness, security, data loss risk)
- **Nit**: Minor style/naming (author's discretion)
- **Optional**: Improvement idea, not blocking
- **FYI**: Context for future readers

---

## Phase 6: SHIP — Deploy Safely

**Principle**: Faster is safer — small, frequent deployments beat big-bang releases.

### Pre-Ship Checklist
- [ ] All Phase 4 exit criteria met
- [ ] All Phase 5 Review feedback addressed
- [ ] Feature flags in place for incomplete/risky work
- [ ] Rollback plan documented
- [ ] Monitoring/alerting in place for new endpoints
- [ ] Database migrations are backwards-compatible

### Git Discipline Before Ship
- Clean git history: one commit per logical change
- Commit messages answer "why", not "what"
- No debug code, console.logs, or commented-out blocks
- No secrets, API keys, or credentials
- Branch rebased onto main (no merge commits for feature work)

### Change Summary Format
When shipping, document:
1. What changed (list of features/fixes)
2. What was NOT changed (scope discipline proof)
3. How to verify (golden path steps)
4. How to roll back

---

## Debugging Mode (when things break)

**STOP → PRESERVE → DIAGNOSE → FIX → GUARD**

1. **Stop adding features** — Don't code around a bug; understand it.
2. **Preserve evidence** — Capture error messages, stack traces, state snapshots before anything changes.
3. **Reproduce reliably** — If you can't make it fail consistently, you don't understand it yet.
4. **Localize** — Which layer? UI / API / DB / external service / the test itself?
5. **Reduce** — Minimal reproduction case. Strip everything unrelated.
6. **Fix root cause** — Ask "why?" 5 times. Fix the cause, not the symptom.
7. **Guard** — Write a test that would fail without your fix.
8. **Verify end-to-end** — Run specific tests + full suite + manual check.

### Common Traps
- Skipping failing tests to unblock other work
- Making multiple unrelated changes during a debug session
- Trusting error messages literally (they describe symptoms, not causes)
- Ignoring flaky tests (they mask real bugs)

    20	def md5(p):
    21	    h = hashlib.md5()
    22	    with open(p, "rb") as f:
    23	        for c in iter(lambda: f.read(65536), b""):
    24	            h.update(c)
    25	    return h.hexdigest()

    27	def snapshot(root):
    28	    """Every regular file + symlink under root: identity that a delete/replace changes."""
    29	    out = {}
    30	    for dp, dns, fns in os.walk(root, followlinks=False):
    31	        for n in fns + dns:
    32	            p = os.path.join(dp, n)

    38	                   "mode": stat.S_IMODE(st.st_mode), "type": "l" if stat.S_ISLNK(st.st_mode)
    39	                   else ("d" if stat.S_ISDIR(st.st_mode) else "f")}

     2	"""Signal-window differential: the 174->175 gap the plain suite is blind to.
     3	
     4	The window between the early exit-0 trap and the `trap '' TSTP TTIN TTOU` is
     5	microseconds wide, so a plain run cannot land a signal in it. This instrument
     6	WIDENS the window identically in every variant (a pure-builtin, SECONDS-bounded
     7	busy-wait -- NOT /bin/sleep, which is itself a killable foreground child and
     8	produces a false BLOCKED) and then delivers the stop signal inside it.
     9

    11	DISCARDS stop signals and every variant would falsely pass.

    15	BUSY = ('_gapwait=$(( SECONDS + 3 )); while builtin [ "$SECONDS" -lt "$_gapwait" ]; '
    16	        'do builtin :; done\n')
    17	TRAP_RE   = re.compile(r"^\s*(builtin\s+)?trap\s+'.*exit 0'.*\bHUP\b")
    18	IGNORE_RE = re.compile(r"^\s*(builtin\s+)?trap\s+''\s+TSTP")

    20	def instrument(src, dst):
    21	    lines = open(src).readlines()
    22	    ti = ii = None
    23	    for i, l in enumerate(lines):
    24	        if ti is None and TRAP_RE.match(l): ti = i
    25	        if ti is not None and ii is None and i > ti and IGNORE_RE.match(l): ii = i
    26	    if ti is None:
    27	        return None, "NO-EARLY-TRAP-ANCHOR"
    28	    ins = (ii if ii is not None else ti + 1)
    29	    out = lines[:ins] + [BUSY] + lines[ins:]
    30	    open(dst, "w").writelines(out)
    31	    os.chmod(dst, 0o755)
    32	    return (ti + 1, ins + 1), ("has-ignore" if ii is not None else "NO-IGNORE-LINE")

    21	    h = hashlib.md5()
    22	    with open(p, "rb") as f:

    27	def snapshot(root):
    28	    """Every regular file + symlink under root: identity that a delete/replace changes."""
    29	    out = {}
    30	    for dp, dns, fns in os.walk(root, followlinks=False):
